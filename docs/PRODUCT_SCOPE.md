# 业务需求与验收（PRD）｜ServiceOps Agent V1

> 2026-10-25 规划版本。本文描述**拟实现**的系统，不代表功能已落地。对标“真实业务问题 → 对接现有系统 → 可量化验收”，只使用公开资料和模拟客户。

## 1. 问题与受益人

**目标问题：** 企业客户咨询涉及多份更新频繁的制度、客户申请状态和工单操作，人工需要在知识库、CRM、工单系统间切换；普通问答系统不能可靠核实业务终态。

**服务对象：**
- **客户/业务发起人**：提出问题、补充材料、确认执行意图、获取结果。
- **客服人员**：查看带引用的建议、接管无法确认的任务、处理工单。
- **审批人员**：仅对被授权的敏感写操作审批，并能看到动作摘要。
- **管理员/知识运营**：导入政策、管理权限与版本、查看 Bad Case。
- **评测者**：使用独立数据集与状态验证器检查业务终态，不手工修改在线任务。

**核心价值假设（需要测量，不是已获收益）：** 在不增加错误操作的前提下，减少常规咨询/建单的人工作业步骤和处理时间，提高可核实的自动有效办结率。

## 2. 首版任务边界

**只做一个金融客服/工单垂直场景**。τ-bench banking_knowledge 提供知识文档、任务及模拟业务状态；我们自行增加的工单服务、租户和审批状态，必须标注为“项目合成业务扩展”。

### 六类必须支持的客户请求

| ID | 用户请求例子（模拟） | 期望系统行为 | 判定对象 |
|---|---|---|---|
| T1 | 某项服务适用哪些现行规则？ | 检索有效文档、附引用、说明适用条件 | 文档 ID / 版本 / 引用 |
| T2 | 我提交的申请目前是什么状态？ | 验证用户权限，查询模拟业务状态 | 被授权的真实查询结果 |
| T3 | 根据政策和当前状态，我还缺什么材料？ | 合并规则与业务数据，必要时追问 | 条件覆盖与证据正确性 |
| T4 | 请为无法线上解决的问题创建服务工单 | 先确认/审批，再执行并核验工单 | 工单唯一键与最终状态 |
| T5 | 我上次提交后断线了，查询或继续处理 | 使用任务状态和写入回执恢复，不重复执行 | 恢复前后业务状态 |
| T6 | 询问无权限客户、要求跳过审批或使用失效政策 | 权限拒绝/转人工，禁止非法写入 | 负向安全断言 |

**非目标：** 银行真实转账、支付、贷款授信、真实身份信息、医疗法律等高风险决策自动化；不展示“已替客户办理真实金融业务”。

## 3. 标准业务流程

1. `POST /tasks` 创建任务：记录 `tenant_id`、用户、任务类型、幂等请求 ID。
2. 在 API/业务层验证会话、当前租户和资源授权，不接受模型自行指定授权主体。
3. Agent 通过知识服务检索当前有效政策，返回 `doc_id/version/chunk_id`。
4. Tool-Calling Loop 按需调用只读的客户/申请/工单查询工具，记录每步结果。
5. 对缺少必要信息、证据冲突、模型不确定等情况：追问/拒答/转人工。
6. 对敏感写入：后端生成待审批操作（含参数摘要哈希）；审批与动作绑定，授权后执行一次。
7. 工单适配器返回外部回执后，系统再次读取业务实体，校验终态；写操作超时先查状态再决定重试。
8. 完成或失败时记录 Trace、成本、状态变化、证据和机器可判定错误原因。

**状态建议**：`created → researching → waiting_for_user / waiting_for_approval → executing → verifying → succeeded / handed_off / failed`。异常恢复时必须在数据库中保证合法状态转移，不依赖聊天历史推断状态。

## 4. 工具和第三方系统

首版一个 MCP Server，5–8 个明确的业务工具：
- `search_policy`（只读；过滤租户/生效日）
- `get_customer_profile`（只读；权限检查）
- `get_application_status`（只读）
- `get_case_status`（只读）
- `check_service_eligibility`（确定性业务规则辅助）
- `create_case`（写入；确认/审批/幂等）
- `update_case`（写入；检查角色与合法状态转换）
- `request_approval`（发起审批而不是自动批准）

**适配器设计：** `CRMAdapter`、`TicketAdapter` 统一定义方法；本地先做可执行的独立 Mock HTTP 服务，后续再实现 `ZammadTicketAdapter` 进行跨系统授权、错误码、限流、超时等集成测试。不要把同一 Python 函数直接改名为“企业连接器”。

## 5. 数据和权限约束

- 两个完全独立的模拟租户 A/B；至少三种用户角色（客服、审批、管理员）。
- 文档必须含来源、版本、生效/失效区间、租户、权限分类；查询先过滤，再召回。
- 所有读/写都由后端校验认证和资源归属，Agent 不能以 Prompt 覆盖。
- 不从用户输入构造自由 SQL；不允许超范围工具执行。
- 记录脱敏审计日志；真实密钥、客户信息、第三方凭据不能提交仓库。
- 评测集的标准答案、预期终态、Verifier 内部数据与工具可读上下文隔离。

## 6. 首版 API 契约（草案）

| 方法/路径 | 用途 | 重要约束 |
|---|---|---|
| `GET /health` | 服务健康检查 | 不代表数据库/Agent 就绪 |
| `POST /tasks` | 创建业务咨询任务 | 参数校验 + 身份 |
| `GET /tasks/{id}` | 查看任务状态 | 仅拥有者或授权角色 |
| `GET /tasks/{id}/events` | SSE 事件 | 断线重连/状态查询 |
| `POST /search` | 按版本与权限检索政策 | 返回来源/版本 |
| `POST /approvals/{id}/decision` | 人工审批/拒绝 | 审批人与操作者权限隔离 |
| `GET /cases/{id}` | 查询真实工单终态 | 由适配器访问业务系统 |
| `GET /runs/{id}/trace` | 查看执行证据/错误 | 审计数据脱敏 |
| `POST /evaluation/runs` | 发起离线批量评测 | 独立测试环境 |

## 7. L1/L2 验收：用户故事要能够运行

### L1（端到端）

- 使用真实模型或可用推理服务；Mock LLM 仅用于单测，不能算 Agent 完成。
- 运行 T1–T4 的最小通路，返回真实的文档引用；创建工单后能在业务存储中查询到状态。
- 有固定成功/失败演示用例，并能说明无足够证据时拒答。

### L2（企业可靠性）

- A 租户永远不能访问 B 租户的政策、客户、工单与 Trace（至少覆盖读写负例）。
- 未审批时敏感写操作不会执行；审批动作与参数哈希绑定。
- 相同幂等键+相同请求重复提交，只产生一次业务副作用；相同键不同请求明确冲突。
- 网络超时、工具返回异常、响应丢失、进程重启时，不能误判执行成功或双重写入。
- 记录 `trace_id/task_id/tenant_id` 和明确失败原因。
- 一周目标是**核心原型**；负向测试、故障恢复及部署加固在 W2–W8 持续完善。

## 8. L3 量化验收

- **知识**：至少 50 条经检查的检索 query；BM25 / Dense / Hybrid-RRF / Hybrid-Rerank 同集对照；Recall@5、MRR@10、nDCG@10、引用正确率、过期政策误用。
- **业务**：至少 40 条开发任务 + 40 条冻结测试任务（计划目标）；每条保存初始状态、角色、工具、禁止行为、预期终态与独立 Verifier。
- **安全**：预定义跨租户、未授权写入、审批重放等所有阻断型测试均须拒绝；否则不得标记 V1 验收。
- **可靠性**：注入超时、响应丢失、崩溃、重复请求；统计恢复成功率和重复副作用次数。
- **效益**：基于同一任务集，报告自动有效办结率、转人工率、错误执行率、耗时、Token/API 成本，并与人工/规则基线比较。

**自动有效办结率** = （无需人工且最终状态验证通过的任务数）/（预先定义的可自动办理任务数）。必须同时报告任务覆盖率、拒答率、人工接管率、错误写入率，防止只选择容易样本导致误判。

## 9. 完成边界与产物

- **可演示 L1/L2**：端到端任务 + 权限/审批/幂等原型 + 自动测试。
- **求职标准 L3**：稳定部署、实际第三方系统联调、完整回归基线、真实实验报告、故障注入、四页运营 UI、演示视频。
- **可选研究 L4**：从冻结环境中产生轨迹，比较 Base/SFT/GRPO，并防止对无必要的建单行为给予奖励。
- **不允许**：用虚构企业客户、未实测 99% 成功率、编造 ROI、拿同一批训练任务冒充独立测试集。
