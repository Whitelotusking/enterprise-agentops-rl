# 开发、验证与版本管理规范

> 业务 PRD → 实际任务 → 可运行代码 → 自动化测试 → 固定演示/实验 → Git 证据。不要靠“学习了某技术”作为完成依据。

## 开发节奏

- 原则上每周 20–30 小时；原理/阅读约 5 小时、开发约 13 小时、测试及失败分析约 5 小时、文档/面试复盘约 2 小时。
- **2026-10-26 至 11-01 是 7 天 L1/L2 原型冲刺**；避免把它与 W2–W10 生产化质量标准混淆。
- 每周先选 1–2 条真实业务用户故事与可观测验收标准，再决定是否引入新技术。
- 开发一条“查询政策→查客户→创建工单→终态核验”的垂直切片后，再增强 RAG 与模型算法。

## 需求优先级

- **P0：** 业务闭环、权威业务状态、FastAPI + DB、证据检索、Agent Tool Loop、后端授权、审批/幂等、独立任务 Verifier。
- **P1：** 实际独立业务系统连接、文档治理、故障恢复、完整 Benchmark、Trace/运营台、成本/性能/部署。
- **P2：** SFT/GRPO、多 Agent、任意规划、高阶分布式设施；无业务需求不得强行加入。

## Git/PR 纪律

- `main` 保持稳定规划和经验证代码；每次独立功能使用短分支与 PR。
- PR 描述至少写明业务目的、变更文件、执行的测试命令/真实输出、残余风险。
- 不要通过“所有测试通过”掩盖没有覆盖 RAG/Agent 的事实；健康检查仅代表 API 存活。
- 实验报告记录 Git commit、模型和数据版本、随机种子、硬件与运行环境。
- 任何性能、准确率或成功率结论都附条件、分母和复现方法。

## WSL 本地环境约定

- 项目开发机使用 PC2 的独立 WSL 发行版 `enterprise-ubuntu`，Linux 项目路径规划为 `/home/enterprise/projects/enterprise-agentops-rl`，WSL 虚拟磁盘位于 Windows `J:\enterprise\wsl`。
- 网络不允许访问 Docker Hub 时可用 WSL 原生 PostgreSQL/pgvector 与 Redis；写清启动命令和实际扩展版本，不能声称 Docker 服务已经运行。
- 当前 WSL 项目可能通过 GitHub ZIP 快照导入，**不保证目录已含 .git 或与远端同步**；开始开发前检查 Git 状态，必要时修复远程同步与 PR 工作流。
- 公开 GitHub 不放置 `.env`、真实 API 密钥、企业私有数据、模型权重或测试答案。

## 质量门槛

- API：Pydantic 校验、鉴权和租户过滤、结构化错误、事务边界。
- RAG：来源、版本、生效范围与权限必须可检查。
- 写工具：审批、幂等、外部结果回查、状态一致性与审计。
- 测试：正常路径 + 无权限 + 失败/超时/重试 + 重启恢复。
- L3：四个可复现检索基线、冻结 Agent 任务、坏案例、P95、Token/API 成本。
- 如果延误，砍掉美观动画、冗余工具和可选训练；**不能删除阻断型安全和终态测试**。

## 成本

- 优先使用 WSL 本地和现有设备；不为项目保持收费 GPU 长期开机。
- 额外云/API 预算约每月 ¥0–100（作为规划约束，而非账单结果），所有调用成本按 run 记录。
- 训练或推理资源不足时降低模型/任务规模、明确未完成项，不捏造实验结果。
