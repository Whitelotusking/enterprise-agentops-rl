# 公开数据、数据治理与评测方案

## 主数据集：τ-bench 系列 / τ-Knowledge（模拟业务数据）

- 官方仓库：<https://github.com/sierra-research/tau2-bench>
- 研究说明：<https://taubench.com/blog/tau-knowledge.html>
- 典型任务：根据政策和业务数据库状态处理模拟的账户、交易、产品或服务请求。
- **必须核实当前仓库的具体 tag/commit、子任务结构、数据许可证和下载方式后再导入**。第一周在 `experiments/dataset_manifest.json` 记录版本，不把无关子任务硬拼到一起。
- 仓库不附带原始测试数据、模型权重与任何真实客户数据；使用时按原项目许可和归属要求执行。

## 数据拆分与版本治理

1. **原始资料**：保持只读，记录来源、许可、下载日期和哈希。
2. **开发集**：自行构造可执行任务、检索问题、业务异常，用于系统开发。
3. **训练集**：独立的成功/失败轨迹，保留产生这些轨迹的工具与模型版本。
4. **验证集**：用于调参、阈值选择和模型选择；在实验前固定。
5. **最终测试集**：独立冻结，答案或预期终态不进入训练、Prompt 样例、向量库或工具返回。
6. **版本锁定**：固定代码 commit、数据 revision、模型 revision、向量模型、随机种子、工具配置。

对于同一企业业务场景中的近重复任务，不能只随机按行切分，还需要按模板、客户/工单实体或任务目标去重分组，减少信息泄漏。

## RAG 评测协议

**建议首轮**：至少约 50 条人工审阅查询（是阶段性开发目标，并非既有数据规模）；关联到确切文档 chunk 与有效时间。

| 版本 | 需要固定的条件 |
|---|---|
| 全文检索（PostgreSQL） | 同一查询集、文档集、过滤条件 |
| Dense Retrieval（pgvector） | 相同 Chunk 与 top-k |
| Hybrid + RRF | 仅增加融合策略 |
| Hybrid + RRF + Reranker | 仅增加重排策略 |

输出 Recall@5、MRR@10、nDCG@10、空结果率、P50/P95 和实例级失败案例。不设定未实测的提升承诺；基线失利时如实记录。

## Agent 评测协议

每条任务固定：初始环境、用户请求、可访问工具、权限状态、成功终态、禁止操作、Verifier。

首版建议构建 **40 条确定性开发任务 + 40 条独立测试任务**，优先覆盖：知识冲突、工具超时、重复写入、越权访问、人工审批、服务重启、多个工具组合、无效操作请求。

核心指标：

- `task_success_rate`：终局状态通过独立 Verifier 的比例。
- `tool_validity_rate`：工具参数符合 schema 且获得业务授权的比例。
- `policy_violation_count`：越权/不合规工具操作数量（期望为零）。
- `recovery_success_rate`：规定的故障注入测试中恢复成功的比例。
- `p50/p95_latency`、模型 token 消耗、失败原因分布。

任务成功与用户可见答复正确必须分别衡量；不能让 Judge LLM 的回答分数代替数据库终态校验。

## SFT 与 GRPO（条件允许）

- `Base`：同模型版本、固定工具定义和执行预算的基础模型。
- `SFT`：训练集成功轨迹转换成结构化工具输出序列。
- `SFT+GRPO`：在训练模拟环境里采样轨迹，使用独立 Verifier 输出任务奖励。
- 如需过程奖励，应证明过程评分与最终正确性一致，不应奖励不必要的工具调用次数。
- 三组实验共享最终测试集、模型家族、工具权限、安全边界和尽可能接近的推理预算。
- 收集 KL、reward、response length、rollout 失败率、任务成功率；消融需说明差异来源。
- 资源不足时可完成 SFT 或小型 GRPO 受控试验，**不可把规则打分或行为克隆称作已经完成了 RL 优化**。
