# 12 周实施路线｜业务驱动的 ServiceOps Agent Harness

> 更新于 2026-10-25。本版替换“以 LangGraph 章节推进”的旧顺序：**业务闭环 → 企业可靠性 → 独立评测与可交付 → 条件允许的训练**。目标是可用于真实面试讨论的公开模拟项目，不假定一周内达到生产级。
>
> 开始前先读 [业务需求与验收](PRODUCT_SCOPE.md)、[技术架构](ARCHITECTURE.md) 和 [数据评测](DATA_AND_EVALUATION.md)。

## 0. 总体约束

- 周期 2026-10-26 至 2027-01-17；原则上每周 20–30 小时（参考 25 小时），**首周 L1/L2 冲刺是激进目标**，不得用省略安全测试伪装完成。
- 核心场景始终是**金融客户服务与工单办理**。首版 1 主 Agent、1 MCP Server、5–8 工具、2 模拟租户、4 页运营 UI。
- GitHub 主干文档与实际代码不同步时，状态以真实 commit、运行记录和测试为准。
- W1 完成 **L1 MVP + L2 核心机制原型**；W2–W8 完成企业能力加固；W9–W10 输出 **L3 可复现的求职展示版本**；W11–W12 是可选 **L4 SFT/GRPO**。
- 2026 年的 JD/面经用于确定要展示的工程能力，并不代表“做完这些就能保证拿 Offer”。

### 首周停工条件与降级原则

若 Docker Hub 或 Git 访问不稳定，优先使用现有 WSL 内 PostgreSQL/pgvector 与受控本地依赖；**不要因为容器镜像拉取阻碍实现 API、RAG 与测试**。若真实模型 API 暂不可用，允许 Mock LLM 测试 Harness，但 L1 的模型验收标记为未通过。前端只需一页工作台原型；Zammad 真实连接放入 W6–W8。

## 2. W2–W10：从原型做到企业可交付

### W2 · 11/02–11/08：业务数据/事务与稳定 API

**做什么**：补齐 schema、迁移和种子数据；客户、申请、工单真实状态转移；分离 MockCRM/MockTicket HTTP 服务；认证、资源级权限和数据库 Session 生命周期。  
**交付**：ER 图、Alembic 迁移、完整 OpenAPI 契约、幂等唯一约束、外部 API 联调测试。  
**验收**：同一工单可通过 API 查询到最终状态；事务回滚正确；非法状态转移拒绝；重复导入不污染数据。  
**面试准备**：为什么不让模型直接执行 SQL？事务/幂等在什么边界保证？

### W3 · 11/09–11/15：可治理的企业知识库

**做什么**：政策来源、版本、有效期、权限范围、元数据、增量更新；知识解析和 Chunk 可追溯；索引失效与重建。  
**交付**：文档生命周期接口、索引管线、数据版本 manifest 与检索结果引用。  
**验收**：新旧版本冲突时只能按日期命中有效版本；两个租户无交叉引用；知识缺失可拒答。  
**面试准备**：为什么纯向量检索不足？如何避免相近业务产品串线？

### W4 · 11/16–11/22：RAG 对照实验与优化

**做什么**：BM25/全文、Dense、Hybrid+RRF、Hybrid+Rerank 的固定基线；Query 改写与上下文截断作为单独消融。  
**交付**：至少 50 条经审阅检索题、统一指标脚本、Recall@5/MRR@10/nDCG@10/P95 报告与 Bad Case。  
**验收**：固定模型、文档版本、过滤器、top-k、评测集；如方法退化如实记录。  
**面试准备**：什么时候检索质量会变差？如何确认模型错误是召回问题而非生成问题？

### W5 · 11/23–11/29：Agent Harness 深化

**做什么**：独立的 Agent Loop、Context Budget、工具路由、拒答/追问/转人工；按需使用 LangGraph 持久化和 HITL。  
**交付**：Runner/ToolAdapter 接口、任务状态、Trace、模型调用预算、Checkpoint/恢复测试。  
**验收**：上下文压缩不会丢失审批约束；至少覆盖工具超时、缺参数、模型错误调用、进程重启。  
**面试准备**：为什么自研循环而不是全部用 LangGraph？哪里需要状态图，哪里直接写确定性代码？

### W6 · 11/30–12/06：MCP 与第三方企业系统连接

**做什么**：独立 MCP Server、工具版本/Schema、超时/重试/熔断；Mock Ticket Adapter 与 [Zammad](https://docs.zammad.org/en/latest/api/ticket/) REST Adapter 的接口对齐。  
**交付**：MCP Client/Server 集成测试、HTTP 适配器、请求关联 ID、错误语义表。  
**验收**：至少有一次独立服务间的真实 HTTP/授权请求；工具失败不能被误报为成功；如无法完成 Zammad 部署，记录原因和未通过项。  
**面试准备**：MCP 和 Function Calling 各自做什么？第三方超时后怎么避免重复创建？

### W7 · 12/07–12/13：多租户、权限与危险写入

**做什么**：JWT、RBAC/资源授权、租户隔离、服务端审批、唯一约束、写入后核验、审计与故障注入。  
**交付**：安全测试矩阵、重复请求/网络失败/审批重放测试、最小权限工具白名单。  
**验收**：**所有阻断型越权/审批/重复写入负例通过**；不能仅靠 Prompt 禁止操作。  
**面试准备**：多租户过滤放在哪层？Checkpoint 能不能代替 DB 事务？如何避免授权被重放？

### W8 · 12/14–12/20：独立 Verifier、Agent Benchmark 与 Bad Case

**做什么**：按租户与任务类型初始化数据库快照；验证最终业务状态而不是 LLM 自评；回收线上模拟失败为回归测试。  
**交付**：40 条开发任务 + 40 条冻结测试任务的目标集、Trace、结果明细 CSV/JSON、错误分析。  
**验收**：记录成功、合理拒答、人工接管和非法行为，区分拒答与自动办结；输出成功率/安全/成本/时延。  
**面试准备**：如何防止测评泄漏？什么是 Reward Hacking？为什么 final answer 正确还可能任务失败？

### W9 · 12/21–12/27：四页业务工作台

**做什么**：React + TypeScript；服务工作台、知识运营、工单管理、AgentOps 运营；SSE 断线恢复。  
**交付**：能串联真实后端业务状态的四页 Web，不以静态假数据填补“已执行”效果。  
**验收**：浏览器执行多步咨询，看到证据、待审批、工单终态、失败原因与历史任务。  
**面试准备**：长任务 SSE 与轮询怎么取舍？前端如何展示任务继续/失败？

### W10 · 12/28–2027/01/03：L3 求职版 V1.0

**做什么**：部署、CI、安全与负载测试、成本与 P95、外部集成证明、系统设计/ADR、演示视频。  
**交付**：可复现部署说明、Docker Compose/WSL 原生方案、完整报告、运行演示、代码/tag。  
**验收**：新环境可根据文档运行；端到端关键业务用例通过；可回答技术选型/失败注入/成本问题；**达到求职作品的主要完成标准**。  
**面试准备**：业务价值怎么衡量？为什么不用多 Agent、Kafka 或 K8s？系统真正瓶颈在哪里？

## 3. W11–W12：可选 L4 算法增量

### W11 · 01/04–01/10：成功轨迹 / SFT

从独立开发环境提取经 Verifier 标记的轨迹，清洗工具 Schema 和负例，LoRA/SFT 训练工具选择；记录训练、验证和冻结测试划分。对比 Base、SFT 的终态成功率、错误写入和成本。资源不足时优先实验可复现，不以训练次数代替贡献。

### W12 · 01/11–01/17：Reward / GRPO 与消融

只有冻结环境可重置、成功奖励可验证且 GPU 预算允许时才做小规模 GRPO。奖励区分“正确办结、合理拒答、合法转人工、非法写入、无必要建单”；比较 Base、SFT、RL，在测试集上记录随机种子、置信区间/样本量和失败。否则交付资源分析与未完成说明，**不宣称完成 RL**。

## 4. 版本验收门槛

| Gate | 标记 | 不能缺少的证据 |
|---|---|---|
| G1 | L1 MVP | 真实模型 + 带引用 RAG + 单 Agent + 工单状态核验 |
| G2 | L2 核心原型 | 租户/审批/幂等和负向测试；首周版本不宣称生产级 |
| G3 | L2 工程加固 | W7 所有阻断型安全测试 + 故障恢复记录 |
| G4 | L3 求职完成 | W10 前后端演示、独立评测、对照、性能、外部适配及可复现交付 |
| G5 | L4（可选） | 训练脚本、配置、隔离数据、真实 Base/SFT/RL 对照与负例 |

优先顺序：**P0 业务闭环/数据正确性/权限/可复现评测 → P1 外部集成/运营台/性能 → P2 SFT/GRPO/多 Agent**。超期只减少工具数量或展示细节，不删除安全和终态验证。每个 Gate 必须在 GitHub 提供真实 commit、测试与记录，不得只通过勾选完成。

## 5. 每周复盘模板

- **业务场景**：本周解决了哪个用户问题？
- **实现内容**：具体模块、接口、测试和代码路径是什么？
- **基线与结果**：固定环境、样本规模、指标与失败案例。
- **技术取舍**：为何采用此方案，试过什么替代方案？
- **本周未通过项**：真实故障和未完成验收。
- **下周优先级**：以用户故事而非技术名词拆解任务。
